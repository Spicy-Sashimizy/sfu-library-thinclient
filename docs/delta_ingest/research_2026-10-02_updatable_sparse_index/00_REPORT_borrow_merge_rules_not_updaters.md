# Borrow engines' merge rules, not their updaters

**Status:** ACTIVE (research input to the delta_ingest track; compiled 2026-10-02, moved from the repository root `research_notes/`/`reports/` 2026-10-10)

**Bottom line:** nobody has an updater for SEISMIC shards that we could lift out and plug into our system. That is true of every product and paper surveyed (Qdrant, Milvus/Knowhere, Vespa, Elasticsearch/Lucene, OpenSearch, Infinity, tantivy, the SEISMIC authors' own code, and the dynamic-index literature through 2026-10). The closest production system is OpenSearch 3.3+, which runs SEISMIC inside a search engine. Even there, nothing updates SEISMIC. Lucene keeps track of new segments, deleted documents and merges, and OpenSearch **rebuilds SEISMIC from scratch for every segment that gets merged** ([neural-search source](https://github.com/opensearch-project/neural-search), [read]). That is the same shape as our delta ingest, and it costs about as much as our rebuild. The only parts of another product we could actually take are small: the "which segments should be merged now" policy (about 150 lines of Rust in tantivy or Quickwit), and a handful of design patterns. A translation layer to a tantivy/Lucene impact index fails if tantivy also answers the sparse queries. Exact SPLADE on inverted indexes runs **tens to hundreds of milliseconds at ~9M documents**, against SEISMIC's sub-millisecond, and stock tantivy cannot even compute the SPLADE score. Used only for bookkeeping, a translation layer works, but it mostly duplicates bookkeeping we already have. The best next step is approach D: keep delta ingest and fix the measured cost of **~20–28 ms added per live generation**. The cost comes from having many small generations, not from how much data is in them. Three patterns used by every engine surveyed address it: one exact mutable tier instead of N small SEISMIC generations, one lexical search across all delta sections instead of one per section, and a merge policy that keeps the number of live generations at one or two.

### Verdicts at a glance

| Approach | Verdict | One-line reason |
|---|---|---|
| **A.** Transplant another product's updater/merge component | **No, except the merge-selection policy** | No surveyed product has an updater that maintains SEISMIC's pruned, clustered lists. Every executor writes only its own format. Only "pick which segments to merge" is a small, format-agnostic piece of code. |
| **B1.** tantivy as updater **and** sparse query path (impact-quantized index) | **Reject** | Exact SPLADE on inverted indexes is ~36–220 ms at 8.8M docs, against ~0.2–0.5 ms for SEISMIC. tantivy hard-wires BM25 and its only pruning method (block-max WAND) is the worst choice for SPLADE. |
| **B2.** tantivy/Lucene as update bookkeeping only, SEISMIC still answers | **Defer; partial yes for the lexical side** | It works (OpenSearch ships it on Lucene), but every merge is still a SEISMIC rebuild. tantivy's plugin hook is unreleased (master only, merged 2026-08-10). The one cheap win is using tantivy's *own* segments and delete bitsets for the delta lexical sections. |
| **C.** Adopt another engine wholesale (background only) | **Not viable on 32–48 GB** | The only published ≥100M learned-sparse deployment with memory figures needs ~1 GB per 1M docs (~150 GB for our corpus), spread over 15 nodes. |
| **D.** Keep delta ingest, refine with patterns from other engines | **Recommended** | The measured overhead is a per-generation fixed cost. Engines bound the number of small tiers rather than make each one cheaper, and our fold-in already reproduces the served shard exactly. |

## No product ships a SEISMIC updater to transplant

To judge approach A, look at what an "updater" actually is in each system. It is the code that accepts inserts, updates and deletes, keeps them somewhere searchable, and periodically merges them into the main index. In every engine surveyed this code is welded to that engine's own file format. Only one small piece comes apart cleanly.

Start with SEISMIC itself. As of 2026-10-02, the upstream TusKANNy/seismic code (MIT, last push 2026-09-10) has **no insert, delete, update or merge API**. Its only `add_document` appends to the dataset *before* the build, and none of its 19 issues requests updates ([TusKANNy/seismic](https://github.com/TusKANNy/seismic), [read]). None of the SEISMIC papers (SIGIR 2024, CIKM 2024, ECIR 2025, ECIR 2026 forward-index compression) mentions updates ([arXiv 2404.18812](https://arxiv.org/pdf/2404.18812), [arXiv 2501.11628](https://arxiv.org/pdf/2501.11628), [arXiv 2602.05445](https://arxiv.org/pdf/2602.05445), [read]). What upstream *has* improved is build speed: the 2026-07-28 commit "Speed up index construction" claims identical output, which makes rebuilds cheaper while still requiring them ([read]). Upstream is worth tracking for build speed, not for an updater.

OpenSearch is the strongest candidate on paper, because it is the only production system that serves SEISMIC and accepts updates. Reading its source answers the question. Lucene does all of the updating: it buffers new documents into new segments, records deletes in a per-segment "live-docs" bitset, and decides when to merge. The SEISMIC code only *builds* a fresh, immutable SEISMIC structure for each segment once that segment reaches `approximate_threshold` (default 1M docs), and rebuilds it at every later merge. The native C++ engine (3.9+, `nsparse`) exposes only `add`, `build` and `search`, with **no `remove`, `delete` or `merge`**. Its merge re-reads the raw vectors of all live documents and calls `build` from scratch ([neural-search](https://github.com/opensearch-project/neural-search), [neural-sparse-cpp seismic_index.cpp](https://github.com/opensearch-project/neural-sparse-cpp/blob/main/nsparse/seismic_index.cpp), [read]). The SEISMIC-specific merge logic in the Lucene engine is about **200 lines of Java** that prune, cluster and summarize. That is exactly what our Rust builder already does ([read] + [inferred]). Running their code as a sidecar would mean running a real Lucene `IndexWriter` just to produce plugin-private `.sit`/`.sip` files, which we would then translate into our own layout. The result would be the same as calling our own `rebuild(forward_vectors)` ([inferred]). Their costs are also in our range. The native engine force-merged 8.8M docs in **1,159 s (19.3 min) versus 3,863 s for the Lucene engine**, and cut JVM heap from 31 GB to 4 GB ([design issue #1802](https://github.com/opensearch-project/neural-search/issues/1802), [snippet], numbers not checked against the raw issue). Our rebuild takes 26 min for an 18.8M-doc shard on 8 threads, so per document a merge in their system costs about what our rebuild does ([inferred]).

The other engines fail the separability test for a more basic reason. **Qdrant's** updater (WAL, appendable segments, ID-tracker deletes, optimizer) is Apache-2.0 Rust. It is embeddable only as the whole local engine via `qdrant-edge` (v0.8.0, 2026-08-05), and it writes Qdrant's private, versioned sparse segment format ([crates.io qdrant-edge](https://crates.io/crates/qdrant-edge), [qdrant lib/sparse](https://github.com/qdrant/qdrant/tree/master/lib/sparse/src/index/inverted_index), [read]). **Milvus's** Knowhere library (Apache-2.0 C++) contains the sparse index but **no tombstone or merge logic**; those live in Milvus's Go and C++ services. Its serialized format was overhauled between 2.6 and 3.0 ([knowhere/src/index/sparse](https://github.com/zilliztech/knowhere/tree/main/src/index/sparse), [read]; format overhaul [snippet]). **Vespa's** and **Infinity's** updaters are in-tree C++ tied to their document models. I found no library form for either ([inferred]). For every one of these, the "translation layer" would have to decode their posting lists and then re-prune, re-cluster and re-summarize into SEISMIC blocks, because SEISMIC needs global per-term pruning. Each translation would therefore end in a SEISMIC build ([inferred]). It would also tie us to a private format that its owner changes freely, which is the opposite of cheap upstream tracking.

What *does* come apart cleanly is merge selection. tantivy's `MergePolicy` trait (MIT) is one function, `compute_merge_candidates(&[SegmentMeta]) -> Vec<MergeCandidate>`, and its `LogMergePolicy` reads only `num_docs`, `num_deleted_docs` and `max_doc`. Quickwit's `StableLogMergePolicy` (Apache-2.0) has the same shape ([tantivy merge_policy.rs](https://github.com/quickwit-oss/tantivy/blob/main/src/indexer/merge_policy.rs), [quickwit merge_policy](https://github.com/quickwit-oss/quickwit/blob/main/quickwit/quickwit-indexing/src/merge_policy/mod.rs), [read]). Either can decide *which* of our generations to compact. The actual merge would remain our own callback: rebuild one SEISMIC shard, one tantivy section, SQLite rows and the abstract store. So would newest-wins resolution and the atomic manifest swap, because no surveyed component provides those for foreign segments ([inferred]). Porting the policy is about 150 lines. Depending on the crate means constructing tantivy `SegmentMeta`s ([read]).

The research literature confirms the picture. The 2024–2026 dynamic learned-sparse work is all either a fresh tier with its own layout, a format-agnostic merge policy, or dense-only. **LinkedBlock** (Rule & Mackenzie, ECIR 2026) indexes SPLADEv3 at ≤~6 µs/doc. It is **insert-only, with no deletes**, and its exact queries are 2–6× slower than static PISA (83.3 ms versus 35.9 ms at 8.8M docs) ([author PDF](https://JMMackenzie.io/pdf/rm26-ecir.pdf), [read]). **Sinnamon/LinScan** handles streaming inserts and deletes on unpruned lists, with no clustering ([arXiv 2301.10622](https://arxiv.org/pdf/2301.10622), [read]). **SPFresh's LIRE** is the only published updater that attacks the failure our in-place SEISMIC updater hit. It splits partitions that grow too large and reassigns vectors locally, instead of reusing slots freed by deletes. Its append-only ablation shows our failure mode: P99.9 latency rose **"from 4ms to more than 10ms because its posting keeps growing"**. With LIRE, only 0.4% of inserts triggered rebalancing, and on average 79 of 5,094 evaluated vectors were reassigned ([arXiv 2410.14452](https://arxiv.org/pdf/2410.14452), [read]). It is, however, dense-only and requires SPDK. One sparse insert would become ~85 per-list block appends, and nobody has checked whether its reassignment conditions hold for SEISMIC's inner-product summaries ([inferred]). **Verdict on A: no.** Take the merge-selection policy; treat LIRE as a research idea, not a component.

## A tantivy translation layer only works for bookkeeping

Approach B has two variants, and they have to be judged separately.

### B1: tantivy maintains *and* answers the sparse leg — reject

The usual way to put SPLADE into a text engine is the "impact" trick. Each token's weight is quantized to an integer and stored as that token's term frequency. Anserini does this on Lucene with `-impact -pretokenized`, repeating each token `cnt` times ([Anserini SPLADE++ regression](https://github.com/castorini/anserini/blob/master/docs/reproduce/from-document-collection/msmarco-v1-passage.splade-pp-ed.onnx.md), [read]). The approach works and updates natively. It is also slow on SPLADE. On MS MARCO (8.8M passages), exact SPLADE takes **~100–220 ms/query single-thread in PISA with MaxScore**, and the block-max WAND family is *slower* (**614 ms versus 121 ms** for MaxScore in the BMP paper's PISA baselines) ([arXiv 2405.01117](https://arxiv.org/pdf/2405.01117), [arXiv 2204.11314](https://arxiv.org/pdf/2204.11314), [read]). The authors of "Wacky Weights" explain why. SPLADE queries carry ~25 unique terms, and they put large weights on subword and stopword tokens (for example, "and" = 225), so "few documents can actually be skipped" ([arXiv 2110.11540](https://arxiv.org/pdf/2110.11540), [read]). Modern Lucene with vectorized block-max MaxScore has caught up with PISA at **36.1 ms on SPLADEv3 at 8.8M docs** ([Rule & Mackenzie, ECIR 2026](https://link.springer.com/chapter/10.1007/978-3-032-21324-2_1), [read]). SEISMIC answers the same kind of collection in **187–531 µs at 90–97% accuracy@10**, against ~100 ms for exact PISA ([arXiv 2404.18812](https://arxiv.org/pdf/2404.18812), [read]). That is roughly a 70–500× gap, depending on which baseline and hardware are compared ([inferred], cross-paper).

tantivy is in a worse position than Lucene. Its term scorer has **BM25 hard-wired** (`K1 = 1.2`, `B = 0.75` as constants, no setter). Its only dynamic-pruning algorithm, block-max WAND, is `pub(crate)` and cannot be reused by a custom query. The per-block maximum it stores is the BM25-maximizing (fieldnorm, tf) pair, with tf clamped at 255 ([tantivy source at 1f9e49da](https://github.com/quickwit-oss/tantivy), `bm25.rs`, `skip.rs`, `boolean_weight.rs`, [read]). With stock tantivy-py, a query built as a sum of `BoostQuery(TermQuery)` therefore scores a saturating, IDF-reweighted function of the impact, not the SPLADE dot product. tf = 10 and tf = 100 differ by about 10%, not 10× ([inferred] from `bm25.rs`). An exact scorer would need a custom Rust `Weight`/`Scorer` with our own MaxScore implementation. The maintainer's answer on the learned-sparse request has been **"no plans at the moment"** since 2024-05-09, and a code search on 2026-10-02 found no SPLADE-on-tantivy project ([issue #2388](https://github.com/quickwit-oss/tantivy/issues/2388), [read]). One of our shards (18.75M docs × 85 ≈ 1.59B postings) is about the posting volume of SPLADEv3 MS MARCO (1.48B). A stock-tantivy BMW query is therefore plausibly **hundreds of ms per shard single-thread**, before our 64-term queries and mmap page faults are counted. Compare the current SEISMIC p50 of ~65 ms across 8 mmap shards (internal figure quoted in the notes). Query-side levers (term pruning, two-phase rescoring) recover **2–7×** in published runs ([OpenSearch two-phase blog](https://opensearch.org/blog/introducing-a-neural-sparse-two-phase-algorithm/), [read via summary]; [arXiv 2405.01117](https://arxiv.org/pdf/2405.01117), [read]). That is not enough to close a 70–500× gap ([inferred, unmeasured on tantivy]).

B1 has two genuine advantages, and both are real. First, an impact index is smaller: **~17–19 bits per posting** in Lucene/PISA, which scales to ~27–31 GB for our 12.75B postings, against ~45–51 bits per nonzero for SEISMIC (≤~72 GB upper bound) ([inferred] from [Rule & Mackenzie](https://link.springer.com/chapter/10.1007/978-3-032-21324-2_1) and [arXiv 2501.11628](https://arxiv.org/pdf/2501.11628)). Second, it updates natively. Neither advantage outweighs the latency, and ingest through pseudo-documents is itself costly: Lucene takes 100–500 µs/doc for SPLADEv3 pseudo-docs, and tantivy is unmeasured ([read]/[inferred]).

### B2: tantivy or Lucene tracks liveness and merges, SEISMIC still answers — feasible, low payoff, defer

This variant is the owner's real question, and it is buildable. OpenSearch is the existence proof: a Lucene `FilterCodec` hooks SEISMIC into Lucene's flush and merge, Lucene supplies live-docs and doc-ID remapping, and SEISMIC answers the queries ([neural-search codec](https://github.com/opensearch-project/neural-search/tree/main/src/main/java/org/opensearch/neuralsearch/sparse/codec), [read]). Lucene's separation of updater and storage format is clean by design, but it brings the JVM.

On tantivy the hook is new and unreleased. **PR #2993 "Extensible segment components via plugin trait"**, written by ParadeDB and merged **2026-08-10**, adds a `SegmentPlugin` that can write custom per-segment files and take part in merges using the merger's doc-ID mapping, which drops deleted documents. ParadeDB says it plans to use it for "custom vector index" ([PR #2993](https://github.com/quickwit-oss/tantivy/pull/2993), [read]). Three caveats apply. It is **not in any release**: the crates.io 0.26.2 tarball (2026-09-08) has no `plugin.rs`, and the next version will be 0.27.0. Opening a writer on an index without the plugin registered **fails closed with `MissingPlugin`**. tantivy-py exposes **no `merge()`, no merge-policy setter and no plugin registration**, and its writer holds a non-blocking exclusive lock ([tantivy-py src/index.rs](https://github.com/quickwit-oss/tantivy-py), [read]). On today's 0.26 the workable shape is clumsier: store the quantized vector as a bytes field, let tantivy's merges carry it along, poll `meta.json` for new segments, and rebuild SEISMIC per merged segment outside tantivy ([inferred]).

Even working perfectly, B2 gives us what we already built: a per-segment live-docs bitset, newest-wins (delete the old copy, add the new one), and a merge scheduler. Every merge is still a full SEISMIC build of the merged segment, and queries still fan out over one SEISMIC index per segment. OpenSearch keeps that fan-out cheap only by keeping segments big (5–10M docs) and leaving small segments as exact, unclustered inverted indexes ([OpenSearch billion-scale blog](https://opensearch.org/blog/scaling-neural-sparse-search-to-billions-of-vectors-with-approximate-search/), [read via summary]). B2 would not remove our ~11 ms/generation sparse fan-out by itself. The design choices in D would. **Verdict on B2:** defer the sparse side until tantivy 0.27 ships and tantivy-py can build with plugins. One part is worth doing now, on the *lexical* side, because tantivy is already our lexical engine: the delta lexical sections could become ordinary segments of one tantivy index, using tantivy's own `delete_term` bitsets for newest-wins (see D). That really is "take the updater of an existing product" for half our stack, and it needs no translation ([inferred], unmeasured).

## Whole-engine adoption does not fit a 48 GB host

This is background only; the owner is not proposing it. It does show why a borrowed updater cannot come with a borrowed engine. The only published learned-sparse deployment at ≥100M docs with memory figures is OpenSearch 3.3 SEISMIC: **1,285,526,507 docs on 15 r7g.12xlarge data nodes, ~53 GB memory per node, 11.77 ms average / 27 ms P99 at 90% recall@10, force merge 2 h 58 m**. The vendor's sizing guidance of **~1 GB per 1M docs** works out to ~150 GB for our corpus, held in JVM heap by the default Lucene engine ([OpenSearch blog, 2025-10-28](https://opensearch.org/blog/scaling-neural-sparse-search-to-billions-of-vectors-with-approximate-search/), [read via summary]). Vespa's fast `wand` needs fast-search weighted-set attributes whose dictionary and postings are **"never paged out to disk"**. Its documented sizing formula gives ~122 GB of attribute data alone for 150M × 85 ([Vespa attributes](https://docs.vespa.ai/en/attributes.html), [read]; arithmetic [inferred]). Qdrant can mmap immutable sparse segments (`memory: cold`/`cached` since v1.19, 2026-08-05), but it publishes no sparse benchmark at ≥100M, and its sparse search is exact ([Qdrant memory tiers](https://qdrant.tech/documentation/ops-configuration/memory-tiers/), [read]). Milvus mmaps sealed sparse segments, keeps growing segments fully in RAM, and its 3.0 SINDI claims (~10× MaxScore QPS) come with no dataset sizes or RAM figures ([Milvus 3.0 blog](https://milvus.io/blog/announcing-milvus-3-lake-native-vector-search-and-a-more-powerful-retrieval-engine.md), [read]). One lesson from this survey matters for us: Qdrant's sparse ingest was quadratic until PR #10682 (2026-09-17) took 1M-point index building **from 250/s to 114,422/s**. That may explain part of earlier "Qdrant is slow at 150M" impressions ([PR #10682](https://github.com/qdrant/qdrant/pull/10682), [read]). Every engine in the survey has the same update architecture: one mutable in-RAM tier, then immutable segments, then tombstones, then background merge ([inferred]). That is the architecture we already have.

## Delta ingest needs fewer generations, not a new updater

The measured overhead of ~20–28 ms per live generation breaks down as ~11 ms sparse fan-out, ~5 ms lexical parse/merge and ~5 ms abstract-store probes. That is a *fixed* cost paid per generation, not a cost of the data in it. External numbers support this reading. FreshDiskANN searches each of its six 5M-point temporary indexes in **0.77 ms**, against 0.89 ms for one 30M index ([arXiv 2105.09613](https://arxiv.org/pdf/2105.09613), [read]). That is about 25× below our per-generation cost for far more data ([inferred]). Amazon's product search moved to Lucene merge-on-refresh because "the small fixed cost of even tiny segments can add up", and got a **~25% reduction in segments searched per query** ([McCandless, 2021-03-19](https://blog.mikemccandless.com/2021/03/open-source-collaboration-or-how-we.html), [read]). Engines never try to make N small tiers cheap. They keep N small, and they make the small tier exact. Four patterns follow.

**One exact mutable tier instead of N small SEISMIC generations.** Qdrant's mutable sparse index is an exact inverted index, and indexing happens only past a size threshold ([Qdrant config.yaml](https://github.com/qdrant/qdrant/blob/master/config/config.yaml), [read]). OpenSearch keeps segments below `approximate_threshold` (default 1M) as plain exact postings ([neural-sparse-ann docs](https://github.com/opensearch-project/documentation-website/blob/main/_vector-search/ai-search/neural-sparse-ann.md), [read]). An exact term-at-a-time scan over a small delta is cheap. The local synthetic benchmark measured **~1.8–2.0 ms p50 at 100k docs and ~9.6–22.6 ms at 1M docs** (single thread, 64-term queries, Zipf 0.8–1.1), using 614 MB of CSC memory at 1M [local-bench]. Scaling PISA's 100.3 ms at 8.8M linearly gives **~5.7 ms at 500k** ([arXiv 2404.18812](https://arxiv.org/pdf/2404.18812), [read]; scaling [inferred]). Sinnamon's measured 4.35–4.68× speedup at 8 threads would bring 1M docs to ~3–6 ms ([arXiv 2301.10622](https://arxiv.org/pdf/2301.10622), [read]; applied [inferred]). On GPU, a June 2026 preprint reports exact SPLADE at **331 µs (100k) and 9.6 ms (8.8M) at batch 1 on an H100**. There is no 16 GB consumer-GPU figure, and the result is unreplicated ([arXiv 2606.26441](https://arxiv.org/html/2606.26441), [read]). The cost of one ~500k-doc exact tier is about what *one* SEISMIC generation costs today, but it is paid once instead of once per generation ([inferred]).

**One lexical search across all delta sections, and abstracts fetched only for the final top-k.** Lucene builds one `Weight` per query with term statistics aggregated across segments, packs small segments into slices of at most 5 segments or 250k docs, shares a minimum-competitive score across them, and fetches stored fields only for the final hits ([Lucene IndexSearcher.java](https://github.com/apache/lucene/blob/main/lucene/core/src/java/org/apache/lucene/search/IndexSearcher.java), [read]; [LUCENE-8992 PR](https://github.com/apache/lucene-solr/pull/904), [snippet]). Our ~5 ms/generation lexical parse/merge fits the opposite pattern, a separate parse and search per section. Our ~5 ms/generation abstract probes have no Lucene equivalent at all ([inferred]). As noted under B2, the natural fix makes delta lexical sections into segments of one tantivy index. tantivy's own delete bitsets then hide superseded base copies, and its default `LogMergePolicy` leaves segments above `max_docs_before_merge` = 10M alone, so large base segments would not be rewritten ([tantivy log_merge_policy.rs](https://github.com/quickwit-oss/tantivy/blob/main/src/indexer/log_merge_policy.rs), [read]). Whether our base lexical index is laid out so that this works was not checked against our code.

**A tiered merge policy that keeps live generations at one or two, triggered by deletes as well as size.** Production defaults allow ~10 segments per tier: Lucene `TieredMergePolicy` uses `segmentsPerTier` = 10 and `deletesPctAllowed` = 20 ([Lucene TMP javadoc](https://lucene.apache.org/core/9_12_0/core/org/apache/lucene/index/TieredMergePolicy.html), [read]), and Qdrant vacuums at `deleted_threshold` = 0.2 ([read]). At +20–28 ms per generation, ten generations would cost +200–280 ms, so our policy must be far stricter than these defaults ([inferred]). tantivy's default `del_docs_ratio_before_merge` = 1.0 means deletes never trigger a merge, which its own source calls "not a very sensible default" ([read]). If the tantivy or Quickwit policy is ported, that knob needs changing.

**Keep the fold-in as a rebuild from forward vectors.** Our fold-in decodes a base shard to vectors and rebuilds it exactly. That avoids a trap visible in OpenSearch's Lucene engine, where merging SEISMIC segments re-prunes the *union of already-pruned lists*: a document dropped from a source segment's top-λ list for a term can never come back ([neural-search SparsePostingsConsumer/MergeHelper](https://github.com/opensearch-project/neural-search), [read]; consequence [inferred]). Change-proportional merging in the style of FreshDiskANN ("a 10% change … in ∼10% of the time" of a rebuild, [arXiv 2105.09613](https://arxiv.org/pdf/2105.09613), [read]) would require re-pruning only the touched posting lists. That is unpublished for SEISMIC, and it pays off little at our churn. With ~42% of a shard's documents new or updated per quarter at ~85 tokens each, nearly every posting list is touched ([inferred]). The rebuild budget is ~26 min × 8 shards ≈ 3.5 h per full quarterly fold-in on 8 threads ([inferred] arithmetic). That is comparable to OpenSearch's 2 h 58 m force merge, which ran on 15 large nodes.

One risk stays open whichever approach is chosen. Deleted documents still inflate SEISMIC block summaries until the fold-in, which wastes work but is safe for recall. If a block's best documents are deleted, though, live documents that static pruning dropped are gone until the rebuild ([inferred] from [neural-search SeismicBaseScorer](https://github.com/opensearch-project/neural-search), [read]). No source measures recall against deleted fraction for SEISMIC.

## Prototype the exact delta tier first

The table ranks what to prototype next. Each row includes the measurement that would prove it wrong.

| Rank | Prototype | Expected effect | What is unverified | Falsified if |
|---|---|---|---|---|
| 1 | Replace live SEISMIC delta generations with **one exact, threaded inverted tier** (u32 id + f32/u16 value), sealed at a size threshold | Sparse delta cost paid once (~5–12 ms single-thread at 500k, ~3–6 ms at 1M on 8 threads) instead of ~11 ms × generations | Our model's real postings-touched fraction on 64-term queries (the benchmark assumed 5–17%); thread scaling on this host; RAM (~0.5–0.7 GB per 1M docs) | On real SPLADE queries against a real 500k–1M delta, 8-thread p50 exceeds **8 ms**, or recall@k of the merged result differs from an exact reference |
| 2 | Put delta lexical sections into **one tantivy index/searcher** (tantivy segments + `delete_term` newest-wins), and fetch abstracts only for the fused top-k | Removes most of ~5 ms lexical + ~5 ms abstract cost per generation | Whether the base tantivy layout allows adding segments without rewriting the base; tantivy-py's lack of merge/policy control | Combined lexical + abstract overhead stays above **~2 ms per remaining generation**, or BM25F scores drift from the current per-section fusion beyond the eval bar |
| 3 | Port tantivy's/Quickwit's **merge-selection policy** (~150 lines) with a deletes trigger near 20% and a hard cap of 1–2 live generations | Bounds latency regardless of ingest pattern | Write amplification under 15% new / 27% updated / 6% deleted per quarter | Compaction work per quarter exceeds the cost of one full fold-in per shard (~26 min), or the cap cannot be held without blocking ingest |
| 4 | **Track tantivy 0.27 `SegmentPlugin`** as the route to B2 (SEISMIC per tantivy segment) | Lets tantivy own liveness and merges for both legs | Release date; tantivy-py plugin builds; API stability | After 0.27 ships, per-segment SEISMIC fan-out over the resulting segments is not cheaper than ranks 1–3 combined |
| 5 | Research only: **LIRE-style split/reassign** for SEISMIC blocks (the in-place idea, done SPFresh's way) | Could avoid rebuilds without the slot exhaustion that killed the bit-level updater | Whether nearest-partition reassignment holds for inner-product summaries; per-doc cost of ~85 list updates | Under the quarterly churn mix, recall drops more than a rebuild's, or per-update cost exceeds rebuild cost amortized per doc |

Approach B1 is not ranked. The evidence against it would be overturned only if a custom tantivy impact scorer reached **≤65 ms p50 on an 18.75M-doc shard with recall equal to SEISMIC's** on our queries. No published result comes within an order of magnitude of that. Approach C is out of scope.

## Conclusion

The idea of plugging in someone else's updater assumed that updaters are generic and formats are local. The survey shows the reverse. The format-specific part (rebuilding pruned, clustered SEISMIC lists) is the expensive part, and nobody has a better way to do it than a rebuild. The generic parts (choosing merges, tombstones, newest-wins) are cheap, and we already have them. What other engines get right, and our delta layer currently does not, is keeping few tiers and making the fresh tier exact. Our 20–28 ms per generation is a per-tier fixed cost that engines avoid by design.

That changes what is worth tracking upstream. TusKANNy/seismic is worth following for build speed, since every update strategy ends in a rebuild. tantivy is worth following for the `SegmentPlugin` release, which is the first credible way to let a maintained, MIT-licensed updater manage SEISMIC segments without a JVM. OpenSearch's neural-search is worth reading for its parameter choices (size threshold, λ scaling with segment size, native mmap engine), not as code to import. The first prototype is cheap to settle: measure one exact tier on real queries against the +8 ms bar.
